# satisfactory-ops 디자인 시스템

이 문서는 배포 화면의 시각 계약이다. CSS 값의 단일 정본은
[`src/styles/tokens.css`](../src/styles/tokens.css)이며, 문서와 코드가 어긋나면
`npm run check:tokens`가 실패한다.

> [!abstract] 제품 인상
> **FICSIT 현장 배포 문서 × 실제 게임 탑뷰 시공판.** 읽는 화면은 판단이 빠른 작업 지시서이고,
> 설계 화면은 게임 안에 그대로 옮길 수 있는 실축 도면이어야 한다.

## 1. 제품과 사용 맥락

- 1차 사용자는 Satisfactory를 혼자 진행하는 한국어 플레이어다.
- 핵심 작업은 `다음 행동 결정 → 공정 설계 → 수치·점유·물류 검증`이다.
- 문서 화면은 빠르게 훑고, 설계 화면은 오래 확대해 보는 중고밀도 도구다.
- 공식 제품처럼 보이게 하지 않는다. 게임 자산은 출처와 권리 고지를 유지한다.
- 게임 이름·수치·크기는 생성된 게임 데이터에서만 온다. 시각 시스템은 사실을 장식으로 덮지 않는다.

## 2. 테마 은유

두 테마는 색 반전이 아니라 서로 다른 작업 환경이다.

| 테마 | 은유 | 기본 사용 |
|---|---|---|
| **라이트 = 정밀 작업지** | 따뜻한 종이, 잉크, 제도선 | 밝은 환경에서 문서·표·도면 검토 |
| **다크 = 현장 제어실** | 청색 편향 차콜, 점등 상태, 장비 패널 | 게임과 전환하며 장시간 사용 |

- 기본은 다크다. 사용자가 고른 값만 `sfops-theme`에 저장한다.
- 모든 공개 화면은 양쪽 테마에서 읽혀야 한다. 일부 화면만 밝아지는 반쪽 테마는 허용하지 않는다.
- 사진·게임 탑뷰 위 지도 마커는 테마와 무관한 `--map-*` 고정 대비층을 쓴다.
- 브라우저 기본 컨트롤은 `color-scheme`을 현재 테마와 동기화한다.

## 3. 토큰 계층

토큰은 세 층으로만 운용한다.

1. `--raw-*`: 팔레트 원시값. `tokens.css` 내부에서만 선언한다.
2. 의미 역할: `--canvas`, `--text-primary`, `--action`, `--status-*`처럼 사용 목적을 말한다.
3. 호환 별칭: `--bg`, `--ink-*`, `--accent` 등 이전 화면 이행용이다. 새 컴포넌트는 의미 역할을 우선한다.

### 강제 규칙

- 색상 리터럴은 `src/styles/tokens.css` 밖에서 0건이어야 한다.
- 소비처에서 `var(--토큰, #대체색)`처럼 원시 색을 폴백으로 넣지 않는다.
- 상태·자원·입출력은 색만으로 구분하지 않고 글자·형태·위치를 병기한다.
- 새 역할이 필요하면 기존 색을 빌려 쓰지 말고 의미 토큰을 먼저 만든다.
- `npm run check:tokens`가 원시 색 누출, 미정의 토큰, 라이트 핵심 역할 누락을 차단한다.

## 4. 색 역할

| 역할 | 토큰 | 사용 |
|---|---|---|
| 앱 바탕 | `--canvas`, `--canvas-grid` | 문서 전체와 희미한 구조 격자 |
| 정보 계층 | `--layer-1..3` | 패널, 들뜬 패널, 선택·오버레이 |
| 본문 | `--text-primary` | 제목·본문·핵심 값 |
| 보조 | `--text-secondary` | 설명·메타데이터 |
| 셋째 | `--text-tertiary` | 캡션·비활성 보조 정보. 작은 글자도 4.5:1 |
| 브랜드 | `--brand`, `--brand-strong` | 경고성 강조와 소량의 FICSIT 오렌지 |
| 행동 | `--action`, `--action-strong`, `--on-action` | 링크·주 행동·포커스 |
| 상태 | `--status-ok/danger/warning` | 검증 결과. 반드시 텍스트와 함께 |
| 의미 경계 | `--border-strong` | 입력·버튼·선택 경계. 인접 면과 3:1 이상 |
| 장식 경계 | `--border-subtle` | 표 행·섹션 구분. 의미 판단에 단독 사용 금지 |
| 도면 실물 | `--diagram-structure`, `--diagram-shadow` | 컨베이어·리프트·기계 층고 |
| 지도 고정층 | `--map-*`, `--node-*`, `--collectible-*` | 지형 사진 위 SVG 마커와 범례 |

오렌지는 면적을 지배하지 않는다. 한 화면의 주요 채움 행동은 하나를 원칙으로 하고,
나머지 행동은 청록 행동색이나 경계선으로 위계를 만든다.

## 5. 접근성 대비 계약

`npm run test:theme`가 빌드 결과를 실제 Chromium에서 계산한다.

| 조합 | 최소 대비 |
|---|---:|
| `text-primary` / `canvas`, `layer-1` | 7:1 |
| `text-secondary`, `text-tertiary` / `canvas`, `layer-1` | 4.5:1 |
| `brand-strong`, `status-*` / `layer-1` | 4.5:1 |
| `on-action` / `action` | 4.5:1 |
| `border-strong` / `layer-1` | 3:1 |

포커스는 `:focus-visible`에서 명확한 행동색 외곽선을 유지한다. 포커스를 숨기는 스타일은 금지한다.

## 6. 타이포그래피

| 역할 | 서체 | 용도 |
|---|---|---|
| 표시 | **Wanted Sans** | 랜딩 헤드라인과 큰 섹션 제목 |
| 본문 | **Pretendard** | 한국어 본문, 표, 컨트롤 |
| 수치 | **JetBrains Mono** | 처리량, 치수, 좌표, 상태 라벨 |

세 서체는 저장소에 서브셋으로 포함한다. 외부 폰트 요청은 없다.

- 기본 본문은 17px, 행간 1.72다.
- 캡션은 13px, 라벨은 12px 아래로 내리지 않는다.
- 수치는 tabular figure가 유지되는 모노 서체를 쓴다.
- 긴 한국어 본문은 `--measure` 또는 `--measure-wide`를 넘기지 않는다.
- 제목은 `text-wrap: balance`, 본문은 좌측 정렬을 기본으로 한다.

## 7. 공간·형태·층위

- 간격은 4px 기반 `--s1`부터 `--s32`까지의 토큰만 사용한다.
- `--s14`는 실축 7m/중간 섹션 간격처럼 56px이 필요한 경우에 쓴다.
- 작은 조작부 `--radius`, 일반 패널 `--radius-m`, 큰 장면 `--radius-l`의 세 단계다.
- 그림자는 장식이 아니라 층위를 설명한다. 헤더·카드·오버레이·대형 미디어 네 역할만 쓴다.
- 도면 점유 경계, 탑뷰 이미지, 포트, 컨베이어는 동일 좌표계에서 맞아야 한다.
- 실제 게임 이미지의 투명 여백을 점유 크기로 착각하지 않는다. 점유 상자가 정본이고 이미지는 그 안에서 정렬한다.

## 8. 이미지와 도면

### 허용

- 게임 설치본·공식 위키에서 출처가 확인된 실제 게임 자산
- 투명 배경 탑뷰, 파운데이션, 벨트·파이프·리프트 작도 자산
- 실제 제품 화면과 앱이 계산한 SVG/PNG 도면

### 금지

- 게임과 무관한 생성형 공장 이미지
- 기계 비율이나 포트 위치를 추측한 합성 이미지
- 점유 상자보다 큰 이미지, 파운데이션 이음새의 인공 흰 선
- 랜딩 장식용 스톡 사진과 근거 없는 아이콘 카드

도면은 설명용 흐름도와 시공용 배치도를 분리한다. 시공용 도면은 실축, 레이어 깊이,
입출력 방향, 처리량, 충돌 여부를 보존하며 독립 SVG/PNG로 내보낼 수 있어야 한다.

## 9. 모션

모션은 `위치 이해`, `상태 변화`, `스크롤 서사` 중 하나를 설명해야 한다.

- 랜딩의 스크롤 장면은 GSAP ScrollTrigger로 핀·스크럽을 구성한다.
- Lenis는 네이티브 스크롤 입력과 접근성을 유지하는 동기화 계층으로만 쓴다.
- DOM/SVG 모션은 transform·opacity를 우선하고 레이아웃 스래싱을 피한다.
- `prefers-reduced-motion: reduce`에서는 최종 콘텐츠를 즉시 보이고 핀과 이동을 제거한다.
- JS가 없을 때도 제목, CTA, 증거 수치, 핵심 설명이 HTML에 그대로 남아야 한다.
- 숫자의 실제 값은 CSS 카운터나 애니메이션이 만들지 않는다.

## 10. 컴포넌트 문법

| 패턴 | 시각 문법 |
|---|---|
| 작업 지시 | 번호 라벨 + 규칙선 + 한 문장 행동 + 검증 근거 |
| 사양 정보 | 모노 라벨/값 2열, 단위 정렬 |
| 상태 | 텍스트 + 점/형태 + 상태색 |
| 주요 행동 | 명확한 채움, 한 장면에 하나 |
| 보조 행동 | 경계선 또는 텍스트 링크 |
| 설계 캔버스 | 중립 격자 + 실물 자산 + 선택/충돌 오버레이 |
| 검사 결과 | 통과·경고·실패를 텍스트와 숫자로 함께 표시 |

## 11. 반응형 계약

- 1440px: 문서 최대폭과 설계 패널을 동시에 활용한다.
- 768px: 표와 도구 패널은 재배치하되 값 열을 한 글자 폭으로 누르지 않는다.
- 390px: 주요 행동과 내비게이션이 가려지지 않고 가로 넘침이 없어야 한다.
- 설계 캔버스는 모바일에서도 축척을 버리지 않는다. 캔버스 자체를 팬/줌하고 주변 UI만 재배치한다.
- 화면 변경 뒤 `squeeze.mjs`와 실제 스크린샷 확인이 필수다.

## 12. 검증 명령

```bash
npm run check:tokens   # 원시 색·미정의 토큰·문서 계약
npm run build
npm run test:theme     # 두 테마 전환·지속·대비
npm run test:nojs      # 값과 핵심 콘텐츠의 HTML 폴백
npm run test:scroll    # 키보드·해시·reduce·GSAP 정리
```

`npm run verify`가 위 검사를 전체 데이터·타입·단위·브라우저 검증과 함께 실행한다.
