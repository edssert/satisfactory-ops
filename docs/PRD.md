## 1. 한 문장

**마일스톤 단위로 "지금 할 일"과 "지금 남겨둬야 할 것"을 알려주는, 내 진행 상황을 아는 Satisfactory 플레이북.**

## 2. 해결하려는 문제

Satisfactory는 설계 게임이다. 초반에 내린 배치 결정이 수십 시간 뒤에 비용으로 돌아온다. 그런데 플레이어가 그 사실을 알게 되는 시점은 이미 늦었을 때다.

구체적으로 반복되는 실패:

| 실패 | 언제 드러나는가 | 원인 |
|---|---|---|
| 로드 밸런서로 지어 확장 불가 | T4~T5 증설 시 | T2에 분배 방식을 잘못 골랐다 |
| 파운데이션 없이 지형에 직접 건설 | T1 파운데이션 해금 시 | 격자 개념을 몰랐다 |
| 나사 라인이 전체 생산을 잡아먹음 | T6 헤비모듈러프레임 | 대체 레시피를 안 모았다 |
| 물이 없어 석탄 발전 불가 | T3 | 입지 선정 시 물을 고려 안 함 |
| 정유소가 부산물 역류로 전면 정지 | T5 | 유체는 양쪽 산출을 다 빼야 한다는 걸 몰랐다 |
| 기차 부지가 없어 공장을 관통 | T6 | T3에 자리를 안 남겼다 |

이 모든 실패의 공통점: **정보가 필요한 시점보다 늦게 도착한다.**

## 3. 기존 도구가 채우지 못하는 것

조사한 도구: satisfactory-calculator.com(SCIM), satisfactorytools.com, ficsit-companion, Ferrumium, satisfactoryplanner.net, satisfactory.th.gl

| 축 | 기존 도구 | 빈틈 |
|---|---|---|
| 생산 비율 계산 | ✅ 매우 잘함 | 없음 — 경쟁하지 않는다 |
| 인터랙티브 맵 | ✅ SCIM이 압도적 | 없음 — 링크로 연결한다 |
| 노드 그래프 플래닝 | ✅ 여럿 있음 | 없음 |
| **진행 순서 안내** | ❌ | **여기** |
| **"왜 그렇게 하는가" 학습** | ❌ | **여기** |
| **내 진행 상황 인지** | ❌ | **여기** |
| **한국어** | ❌ 대부분 영문 | **여기** |

결론: 계산기를 더 잘 만드는 것이 아니라, **순서와 근거와 맥락**을 제공한다.

> 벤치마킹 상세와 근거는 `docs/DIFFERENTIATION.md` 참조.

## 4. 대상 사용자

### 4.1 1차 — 진행 중인 플레이어 (개인 사용 포함)
게임을 켜놓고 두 번째 화면 또는 알트탭으로 본다. "지금 T3인데 뭘 먼저 해야 하지?"에 즉시 답을 얻고 싶다.

- **핵심 요구**: 빠른 로딩, 오프라인 동작, 내 진행도 기억
- **사용 빈도**: 플레이 세션마다

### 4.2 2차 — 시작을 앞둔 플레이어
"어디에 베이스를 지어야 하나"부터 막힌다. 선택지의 근거를 원한다.

- **핵심 요구**: 입지 비교, 근거 제시, 지도
- **사용 빈도**: 1회성이지만 결정의 무게가 크다

### 4.3 3차 — 재시작하는 플레이어
한 번 실패해봤고, 이번엔 제대로 하고 싶다. 원칙과 함정 목록을 원한다.

- **핵심 요구**: 설계 원칙, 단계별 배치도, 흔한 실패

## 5. 제품 범위

### 5.1 포함 (v1)

| # | 기능 | 우선순위 |
|---|---|---|
| F1 | 마일스톤 진행 체크리스트 (T0~T9, 진척 저장) | P0 |
| F2 | 입지 선정 — 실제 게임 맵 + 그리드/핀 오버레이 | P0 |
| F3 | 공장 성장 단계도 — 배치·배관·배선 다이어그램 | P0 |
| F4 | 용어집 — 학습 레이어 (매니폴드 등) | P0 |
| F5 | 생산 라인 계산기 — 목표 개/분 → 기계 수 역산 | P1 |
| F6 | 레퍼런스 표 — 레시피·전력·물류 수치 | P1 |
| F7 | 대체 레시피 확보 체크 + 계산기 연동 | P1 |
| F8 | 하드드라이브 수집 계획 | P1 |
| F9 | **공장 상태 관리** — 지은 라인과 생산량 기록 | P2 |
| F10 | **세이브 파일(.sav) 임포트** — 진행도 자동 반영 | P2 |
| F11 | 랜딩페이지 | P1 |
| F12 | 진척 내보내기/가져오기 | P2 |
| F13 | **공장 설계 도면 생성** — 목표 → 격자 배치 → 도면 → 건설 순서 | P0 |

### 5.2 제외 (v1에서 하지 않음)

- 노드 그래프 편집기 (기존 도구가 잘함)
- 사용자가 직접 그리는 자유 배치 캔버스 (기존 도구가 잘함 — `research/layout-design-tools.md` §2)
- 세이브 파일 편집 (읽기만 한다)
- 블루프린트 **파일(.sbp) 생성·공유** — 도면 생성(F13)과는 별개다. MIT 파서로 기술적으로 가능해 보이나
  백지 생성의 실현 가능성이 검증되지 않았다(연구 문서 §3). 검증에 성공하면 그때 범위에 넣는다
- 3D 렌더링·미관 설계
- 멀티플레이어 협업
- 서버 계정·로그인

### 5.3 명시적 비목표

- **계산 정밀도 경쟁을 하지 않는다.** 복잡한 최적화는 satisfactorytools로 연결한다.
- **위키를 대체하지 않는다.** 전수 데이터베이스가 아니라 진행 안내서다.

## 6. 사용자 결정 사항 (확정)

> 2026-08-19 확정. 변경 시 이 절을 갱신하고 영향받는 ADR을 supersede 한다.

| 질문 | 결정 | 영향 |
|---|---|---|
| 대상 | **공개 제품 + 개인 진행 추적 1급** | 랜딩페이지·온보딩 필요. 공유 기능은 P2 |
| 세이브 파일 연동 | **구현한다** | 브라우저 .sav 파서 필요 → ADR-0014, 범위는 리서치 결과에 따라 조정 |
| 진행 추적 깊이 | **공장 상태까지 관리** | 사용자 데이터 모델이 커짐 → 영속성 계층이 중요해짐 |
| 언어 | **한국어 + 게임용어 영문 병기** | UI 전환 없음. 용어 병기 규칙을 데이터 스키마에 반영 |

## 7. 성공 기준

### 7.1 정성
- 플레이어가 **되돌아가서 뜯는 일**이 줄어든다 — "이걸 미리 알았더라면"이 사라진다
- 용어를 모르는 사람이 앱을 읽고 이해할 수 있다
- 게임을 켜둔 채 참조하는 것이 부담스럽지 않다

### 7.2 정량 (v1 목표)
| 지표 | 목표 | 이유 |
|---|---|---|
| 초기 로딩 (3G Fast) | < 3초 | 알트탭 사용 맥락 |
| 첫 화면 렌더 | < 1.5초 | 같음 |
| 오프라인 동작 | 전 기능 | 게임 중 네트워크 불안정 가능 |
| 검증된 수치 비율 | 100% (`disputed` 제외) | 신뢰가 제품의 전부 |
| 모바일 사용 가능 | 세로 화면에서 전 기능 | 태블릿·폰 참조 |

## 8. 리스크

| 리스크 | 영향 | 완화 |
|---|---|---|
| 게임 업데이트로 수치 변경 | 데이터 전면 무효화 | `Docs.json` 기반 생성 파이프라인 → 재생성으로 대응 (ADR-0008) |
| .sav 포맷 변경 | 세이브 임포트 파손 | 지원 버전 명시 + 실패 시 수동 입력으로 후퇴 (ADR-0014) |
| 1.2 자원 랜덤화 사용 세이브 | 입지·노드 조언 무효 | 랜덤화 감지 시 해당 기능에 경고 표시 |
| 게임 자산 저작권 | 저장소 삭제 요구 | 출처 표기, 비상업, 요청 시 제거 (LICENSE 명시) |
| 1인 개발 유지보수 | 방치 | 의존성 최소화, 빌드 없는 구조 우선 (ADR-0009) |

## 9. 열린 질문

- 공장 상태 관리(F9)의 입력 부담을 어떻게 줄일 것인가 — 세이브 임포트가 답이 될 수 있으나 실패 시 대안 필요
- 대체 레시피 선택이 계산기·추천에 반영되는 범위를 어디까지 할 것인가
- 랜덤화 세이브 사용자를 위한 대체 경험을 만들 것인가, 경고만 할 것인가
