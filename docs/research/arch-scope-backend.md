# 백엔드 필요성 조사 — satisfactory-ops

조사일: 2026-08-19
조사자: 기술 리서처 (백엔드 필요성 담당)

## 결론 먼저

**이 앱에 백엔드는 필요 없다.** 6개 예정 화면(마일스톤 체크리스트, 입지 선정, 성장 단계도, 생산 라인 계산기, 용어집, 레퍼런스 표) 중 서버 없이 못 만드는 것은 하나도 없다. GitHub Pages(정적 호스팅) + 브라우저 저장소(localStorage/IndexedDB) + URL 인코딩 공유로 요구사항을 전부 충족한다. `.sav` 세이브 파일 파싱은 애초에 이 앱의 스펙에 없으며, 있다 하더라도 현재 생태계에 "가볍게 가져다 쓸 수 있는 브라우저용 파서"가 없어 백엔드를 정당화하는 근거가 되지 못한다.

## 1. 진척 상황 동기화 — 기기 간 동기화가 정말 필요한가

- 사용 맥락 자체가 "알트탭으로 흘끗 보는 두 번째 모니터"다. 세션 중 기기를 바꿔가며 체크리스트를 보는 시나리오는 드물다(같은 PC의 같은 브라우저에서 계속 씀). 진짜 니즈는 "같은 기기·같은 브라우저에서 진척이 안 날아가는 것"이지 "PC↔폰 실시간 동기화"가 아니다.
- `localStorage`(또는 `IndexedDB`, 데이터가 커지면)로 브라우저에 영구 저장하면 동일 기기에서는 재방문해도 유지된다. 오프라인에서도 완전히 동작 — 오프라인 요구사항과도 정확히 맞는다.
- 기기를 바꾸는 소수 케이스(PC→태블릿)는 "내보내기(JSON 다운로드) → 가져오기(파일 업로드)" 버튼 하나로 해결된다. 구현 비용은 JSON.stringify/parse 수준이고, 계정·로그인·서버 DB가 전혀 필요 없다.
- 백엔드로 실시간 동기화를 하려면 인증(계정), DB, API 서버, 그리고 그걸 GitHub Pages와 별도로 배포·유지보수해야 한다 — 개발자 1인 체제의 "유지보수 부담이 실질적 제약"이라는 전제와 정면으로 충돌한다. 이득(가끔 있는 기기 전환 편의) 대비 비용(상시 운영 부담)이 맞지 않는다.

**권고**: `localStorage` 자동 저장 + "진행 상황 내보내기/가져오기(JSON)" 버튼. 계정 시스템 없음.

## 2. `.sav` 세이브 파일 파싱 — 브라우저에서 가능한가

먼저 확인할 것: 프로젝트 스펙(화면 ①~⑥)에는 세이브 파일 가져오기 기능이 없다. 이 조사는 "혹시 백엔드가 필요해지는 시나리오인가"를 검증하기 위한 것이며, 결론적으로 **범위 밖 기능이고, 넣더라도 서버 없이 하기엔 부담이 크다.**

GitHub에서 관련 오픈소스 프로젝트를 실제로 확인한 결과:

| 저장소 | 언어/형태 | 라이선스 | 실행 환경 | 최근 커밋 |
|---|---|---|---|---|
| `ficsit-felix/satisfactory-json` | TypeScript | MIT | **Node.js 전용** — Node 스트림 API에 의존, 브라우저에서 직접 동작 안 함(README에 명시) | 2022-02 (마지막 push), Satisfactory 1.0(2024-09 정식 출시) 이전 |
| `Goz3rr/SatisfactorySaveEditor` (★305, 가장 인기) | C# | 라이선스 미명시 | **데스크톱 앱(WPF)** — 웹/브라우저 아님 | 2024-08 |
| `AyrA/SatisfactorySaveEditor` | — | — | 데스크톱 | — |
| `R3dByt3/SatisfactorySaveNet` | C# | — | .NET 라이브러리, 브라우저 아님 | — |
| `GreyHak/sat_sav_parse` | Python | — | 서버/스크립트용, 브라우저 아님 | — |

즉 "이미 존재하는 클라이언트 사이드(브라우저) 세이브 파서를 가져다 쓴다"는 전제 자체가 성립하지 않는다. 가장 근접했던 `satisfactory-json`조차 Node 전용이고 4년 넘게 방치되어 있어 Satisfactory 1.0 이후의 세이브 포맷 변경을 반영했는지 검증되지 않는다(포맷은 Early Access 내내 버전마다 깨지는 변경이 있었다고 README에 명시).

세이브 포맷을 직접 리버스엔지니어링해 순수 JS/WASM 파서를 새로 작성하는 것은 가능은 하지만(바이너리 청크 포맷이라 이론적으로는 `ArrayBuffer`/`DataView`로 브라우저에서 파싱 가능), 이는:
- 이 프로젝트의 핵심 목적("지금 뭘 해야 하는지 알려주는 플레이북")과 무관한 별도 프로젝트급 작업이고,
- 파싱 자체는 클라이언트 사이드로 가능하다 해도(즉 백엔드가 필요한 이유가 되지도 않고),
- 유지보수 부담(게임 업데이트마다 포맷 깨짐 추적)만 늘린다.

**권고**: `.sav` 파싱 기능은 스코프에 넣지 않는다. 넣게 되더라도 "서버로 업로드해서 파싱"이 아니라 "브라우저에서 `File` API로 읽어 클라이언트에서 파싱"이 유일하게 이 프로젝트의 원칙(오프라인, 서버 없음)과 맞는 방향이며, 그마저도 별도 스파이크로 취급해야 한다.

## 3. 빌드/설계 공유 — URL 인코딩으로 충분한가

- 공유 대상은 "그리드/핀 위치, 체크리스트 상태, 생산 라인 계산기 입력값" 같은 작은 구조적 데이터다. 이미지·바이너리가 아니라 숫자/키 배열이므로 JSON 직렬화 후 `LZ-String` 등으로 압축 + `URLSearchParams`나 fragment(`#`)에 넣으면 수백 바이트~수 KB 수준으로 충분히 URL에 들어간다. 이 패턴은 Factorio 블루프린트 사이트, 각종 빌드 계산기(예: PoE/Diablo 빌드 플래너)들이 표준적으로 쓰는 방식이다.
- URL fragment(`#...`)에 넣으면 GitHub Pages 서버로 전송조차 되지 않고 순수 클라이언트에서만 파싱된다 — 로그·서버 비용 0.
- 저장소(서버 DB)가 필요해지는 경우는 "짧은 단축 URL을 발급하고 싶다" 또는 "공유된 빌드를 검색/목록화하고 싶다" 같은 부가 기능일 때뿐인데, 현재 스펙에 그런 요구는 없다.

**권고**: 공유 기능은 압축된 상태를 URL fragment에 인코딩하는 방식으로 구현. 별도 저장소 불필요.

## 4. 그래도 서버가 필요해질 경우 — 무료 티어 실측 (2026-08 기준)

혹시 향후 요구사항이 늘어(예: 커뮤니티 빌드 공유 목록, 코멘트 등) 서버가 필요해질 가능성에 대비해 무료 옵션을 실측했다.

**GitHub Gist API (Gist를 저장소로 쓰는 안)**
- GitHub 공식 문서 기준, gist **생성/수정은 반드시 인증 필요**("you must be signed into GitHub to create gists") — 완전 익명 클라이언트에서 직접 API로 새 gist를 못 만든다. 즉 "정적 페이지에서 그냥 fetch로 Gist에 쓴다"는 방식은 성립하지 않고, 최소한 OAuth 토큰을 안전하게 다루는 중개 레이어(=사실상 백엔드나 서버리스 함수)가 필요해진다. 읽기(공개 gist 열람)는 익명으로 가능.
- 결론: Gist API는 "공유 데이터를 서버 없이 쓰기(write)"에는 못 쓴다. 순수 조회용 백업 채널 정도로만 의미가 있다.

**Cloudflare Workers 무료 티어 (2026-08 기준 공식 문서)**
- 요청: 100,000회/일
- CPU 시간: 요청당 10ms 무료
- Workers KV: 읽기 100,000/일, 쓰기 1,000/일, 삭제 1,000/일, 저장 용량 1GB
- D1(SQLite): 읽기 500만 행/일, 쓰기 10만 행/일, 저장 5GB
- 매일 UTC 0시 리셋
- 평가: 개인 프로젝트/소규모 커뮤니티 트래픽에는 넉넉하다. 다만 KV 쓰기 1,000/일 한도는 "빌드 공유를 자주 저장"하는 기능을 넣으면 빠듯할 수 있음(사용자당 1일 1~2회 저장이면 충분).

**Supabase 무료 티어 (2026-08 기준)**
- DB 500MB, 공유 CPU/RAM 500MB
- **7일간 활동 없으면 프로젝트 자동 일시정지** — 개인 사이드 프로젝트처럼 트래픽이 뜸하면 정기적으로 깨어나야 함(수동 재개 필요), 이게 "플레이 중 알트탭으로 즉시 봐야 한다"는 요구사항과 상충할 위험이 있다(정지된 프로젝트는 첫 요청이 실패하거나 느리게 응답).
- 무료 프로젝트 최대 2개, 월 egress 5GB, 파일 저장 1GB
- 평가: 진짜 관계형 DB/인증이 필요해지면 후보가 되지만, 자동 일시정지 정책이 이 앱의 "즉시 반응해야 함" 요구와 안 맞아 1순위로 권하지 않음. Cloudflare Workers + KV/D1 쪽이 "항상 켜져 있음" 특성상 더 적합.

## 종합 권고 (구체적)

1. **서버 없음이 정답.** GitHub Pages 정적 배포를 그대로 유지한다.
2. 진척 저장: `localStorage` 자동저장 + "내보내기/가져오기(JSON)" 버튼 1쌍. 계정/로그인 없음.
3. 빌드/입지/계산기 설정 공유: 상태를 JSON → LZ-String 압축 → URL fragment(`#state=...`)에 인코딩. 서버 전송 없이 클라이언트에서만 인코딩/디코딩.
4. `.sav` 세이브 파일 가져오기 기능은 **이번 스코프에서 제외**. 이유: (a) 기존 스펙에 없던 기능이고, (b) 클라이언트 사이드로 재사용 가능한 성숙한 파서가 현재 생태계에 없으며(`ficsit-felix/satisfactory-json`은 Node 전용이고 2022년 이후 방치), (c) 백엔드를 정당화할 근거도 되지 않는다(파싱 자체는 어차피 클라이언트에서 하게 될 일).
5. 향후 정말로 "커뮤니티 공유 목록" 같은 서버 필요 기능이 생기면, GitHub Gist API는 쓰기(write)에 인증이 필요해 단독으로 못 쓰고, Supabase는 7일 비활성 시 자동 일시정지되어 즉시성 요구와 충돌하니, **Cloudflare Workers + KV(또는 D1)** 를 1순위 후보로 남겨둔다. 단, 지금 스펙 안에서는 이조차 필요 없다.
