> satisfactory-ops / 담당: 기술 리서처(성능·접근성·i18n)
> 작성일 2026-08-19

---

## 0. 요약

- **이미지**: webp만으로 충분하다(이미 400KB+170KB, avif는 이득 대비 인코딩/폴백 비용 낭비). `<picture>` 다중 소스는 과설계 — 지금 자산 규모에서 불필요.
- **초기 로딩 예산**: 알트탭 재방문이 핵심 시나리오이므로 진짜 목표는 "첫 로딩"이 아니라 "캐시 히트 후 콜드 스타트". 서비스워커 프리캐시 + `loading="lazy"`는 초기 화면(체크리스트) 기준으로만 적용하고 맵 이미지엔 걸지 않는다.
- **GitHub Pages 캐시**: 커스텀 헤더 불가, `Cache-Control: max-age=600` 고정(10분) — 캐시 버스팅은 파일명 해시나 쿼리스트링이 아니라 **서비스워커의 버전 관리**로 해결해야 한다.
- **맵 줌/팬**: CSS `transform: translate3d() scale()` 직접 구현으로 충분하다. 라이브러리(`panzoom` 등) 없이 120~150줄이면 핀치줌·드래그·휠줌 다 구현 가능 — 무빌드 원칙과 정합.
- **접근성**: 자원 색상 구분은 색상 단독 금지(WCAG 1.4.1) — 아이콘/패턴/텍스트 라벨 병행 필수. `prefers-reduced-motion`은 맵 팬/줌 애니메이션에 직접 영향.
- **i18n**: 무빌드 환경에서 실용적 구조는 **JSON 딕셔너리 + `data-i18n` 속성 치환**. 게임 용어는 국문 표기 후 괄호 영문 병기가 관행.

## 1. 성능

### 1.1 이미지 포맷 — webp/avif

이미 webp로 번들되어 있고 용량이 작다(맵 400KB, 아이콘 170KB — 합 570KB). 이 규모에서 avif 추가 인코딩은 실익이 없다.

- WebP는 JPEG 대비 25~35%, PNG 대비 최대 80% 용량 절감 사례가 보고됨(YouTube 썸네일, Facebook 사례).
- `<picture>` + 다중 `<source>`로 포맷 폴백을 주는 패턴이 표준이지만, 이는 **구형 브라우저 지원**이 목적이다. 이 앱은 "알트탭용 개인 도구"이고 사용자가 자기 브라우저를 통제하므로, webp 단일 포맷 + `<img>` 하나로 충분하다. 다중 소스 관리 비용(1인 유지보수 제약)이 이득보다 크다.

### 1.2 반응형 srcset — 이 프로젝트엔 낮은 우선순위

`srcset`/`sizes`는 "같은 이미지의 여러 해상도 변형을 두고 뷰포트에 맞는 걸 고른다"는 게 핵심 가치다. 이 앱의 이미지 두 종류를 보면:

- **맵 이미지(2장, ~400KB)**: 확대해서 보는 게 목적이라 애초에 고해상도 원본이 필요하다. 축소 변형을 따로 둬도 "화면이 작을 때만 저해상도"가 의미가 없다 — 태블릿에서도 확대해서 디테일을 본다. srcset 이득이 없다.
- **건물 아이콘(27개, ~170KB, 개당 ~6KB)**: 이미 작아서 반응형 변형을 만드는 관리 비용이 파일 크기 이득을 넘어선다.

**권고**: srcset은 도입하지 않는다. 대신 아이콘을 하나의 스프라이트시트나 SVG 심볼 세트로 합치는 쪽이 이 자산 규모에는 더 실용적(요청 수 27→1).

### 1.3 lazy loading — 어디에 걸고 어디에 걸지 않을지

`loading="lazy"`의 동작 확인:
- 뷰포트 밖 이미지의 다운로드를 지연시켜 초기 로드 대역폭을 절약한다.
- `width`/`height`(또는 `aspect-ratio`)를 반드시 명시해야 한다 — 없으면 로드 시 레이아웃 시프트(CLS 악화)가 발생한다.
- JS가 꺼져 있으면 지연 로딩 자체가 비활성화된다(안티트래킹 조치) — 즉 항상 브라우저 네이티브 속성만으로 충분하고, JS 폴리필은 불필요하다.
- `window.load` 이벤트가 지연 로딩된 이미지를 기다리지 않는다 — "로딩 완료" 판단 로직을 이 이벤트에 의존하면 안 된다.

**화면별 적용**:
- ① 체크리스트, ⑤ 용어집, ⑥ 레퍼런스 표: 건물 아이콘에 `loading="lazy"` + `width`/`height` 고정 — 표가 길면 이득이 있다.
- ② 입지 선정 맵: **lazy 걸지 않는다.** 화면 진입 즉시 필요한 단일 리소스이고, 오히려 진입 시점에 즉각 프리로드(`<link rel="preload">` 또는 서비스워커 프리캐시)하는 게 맞다.
- ③ 공장 성장 단계도: 단계 전환 시 필요한 이미지만 그때 그때 로드 — lazy 적합.

### 1.4 초기 로딩 예산

플레이 중 알트탭이라는 사용 맥락에서 실제로 중요한 지표는 "최초 방문 로딩"이 아니라 "재방문 콜드 스타트"다. 예산을 두 겹으로 나눠 잡는 게 맞다.

| 시나리오 | 목표 | 방법 |
|---|---|---|
| 최초 방문(온라인) | FCP < 1.5s, 총 전송량 < 1MB(현재 자산 합과 일치) | 이미지·JSON 모두 압축 상태 그대로 전송, 빌드 단계 없이 원본 서빙 |
| 재방문(알트탭, 오프라인 가능) | 콜드 스타트 수십 ms, 네트워크 왕복 0 | 서비스워커로 전체 자산 프리캐시 — "설치 후엔 로딩 화면 자체가 없다"가 목표치 |

체크리스트 진행 데이터처럼 자주 바뀌는 상태는 `localStorage`/`IndexedDB`로 로컬 저장(이미 다른 조사 문서에서 다룸), 정적 자산은 SW 프리캐시. 이 조합이면 "느리면 안 쓴다"는 요구를 실제로 만족시키는 유일한 방법이다 — CDN을 아무리 잘 써도 온라인 왕복이 있는 한 알트탭 체감 속도를 이기지 못한다.

### 1.5 GitHub Pages 캐시 헤더의 제약

- GitHub Pages는 **커스텀 응답 헤더를 설정할 수 없다**(Netlify의 `_headers` 같은 기능 없음). 실제 응답은 `Cache-Control: max-age=600`(10분)으로 고정되어 나간다. Fastly CDN을 경유하며 ETag 기반 재검증이 붙는다.
- 배포 후 CDN·캐시 전파에 **최대 10분** 지연이 있을 수 있다고 GitHub 공식 문서가 명시한다("It can take up to 10 minutes for changes to your site to publish after you push").
- 결론: **파일명 콘텐츠 해시를 통한 캐시 버스팅은 GitHub Pages 자체 캐시엔 원래도 필요 없다**(max-age가 10분으로 짧아 자연 재검증됨). 캐시 버스팅이 진짜 필요한 지점은 **서비스워커가 관리하는 오프라인 캐시**다 — SW의 `CACHE_VERSION` 문자열을 배포마다 올려서 `activate` 단계에서 구 캐시를 지우는 패턴을 쓴다. HTTP 캐시가 아니라 SW 캐시 버전을 갱신 신호로 삼는 게 맞다.

## 2. 맵 줌/팬 구현

### 2.1 방식 비교

| 방식 | 적합성 | 근거 |
|---|---|---|
| **CSS `transform`(translate/scale) 직접 구현** | ✅ 채택 | GPU 컴포지팅 단계에서만 처리되어 레이아웃·리페인트를 유발하지 않음 — 60fps 확보에 충분. `translate3d(x,y,0) scale(s)` 패턴이 표준. 핀 오버레이가 SVG면 부모 컨테이너에 같은 transform을 걸어 이미지와 SVG가 함께 움직이게 하면 됨. |
| **Canvas 재렌더링** | ❌ 기각 | 매 프레임 직접 픽셀을 그려야 하고, 접근성(핀에 title/aria, 키보드 포커스)을 canvas 내부 요소에 줄 수 없어 별도 DOM 오버레이가 어차피 필요함 — 이점 없이 복잡도만 증가. |
| **외부 라이브러리(`panzoom` 등)** | ⚠️ 불필요 | `anvaka/panzoom`은 DOM·SVG 모두 지원, 마우스휠/드래그/핀치줌/키보드까지 기능은 좋지만, 무빌드·의존성 0 원칙과 상충. 기능 목록 자체가 "직접 구현해야 할 이벤트 핸들러 체크리스트"로는 유용 — 구현 시 이 라이브러리의 옵션 이름(`pinchSpeed`, 더블클릭 줌 등)을 참고해 자체 구현의 기능 커버리지를 맞춘다. |

### 2.2 자체 구현 설계 요점

- `will-change: transform`은 상시 켜두지 말고, 팬/줌 인터랙션이 **시작될 때** 켜고 **끝나면** `auto`로 되돌린다(메모리 낭비 방지) — `pointerup`/`transitionend` 훅으로 처리.
- 확대 중심점: `transform-origin`을 커서/터치 위치로 갱신하여 "커서 아래 지점이 고정된 채 확대"되는 자연스러운 줌 구현.
- 터치: `pointerdown/move/up` 통합 Pointer Events로 마우스·터치·펜을 하나의 핸들러로 처리 가능(별도 touch 이벤트 분기 불필요) — 핀치줌은 두 번째 포인터의 거리 변화로 스케일 계산.
- 경계 클램핑: 이미지가 뷰포트 밖으로 과도하게 벗어나지 않도록 `translate` 값을 이미지/컨테이너 크기 기준으로 clamp.

**결론**: 무의존 구현이 실제로 가능하고, 이 프로젝트 성격(1인 유지보수, 무빌드)에는 오히려 라이브러리보다 우월하다. 예상 규모 120~150줄.

## 3. 접근성

### 3.1 키보드 내비게이션

- 마일스톤 체크리스트, 용어집, 레퍼런스 표는 전부 시맨틱 HTML(`<button>`, `<table>`, `<a>`)로 구성하면 기본 탭 순서만으로 대부분 해결된다.
- 맵 화면의 핀은 시각적으로는 SVG/CSS로 배치되지만 **각 핀이 실제 포커스 가능한 요소**(예: `<button>` 오버레이 또는 `tabindex="0"` + `role="button"`)여야 한다. 확대/축소 자체도 `+`/`-`/화살표 키로 조작 가능하게 만드는 게 `panzoom` 류 라이브러리의 공통 관행이다.

### 3.2 다크/라이트 테마

- `prefers-color-scheme` 미디어쿼리로 시스템 설정을 기본값으로 따르고, 수동 토글은 로컬 저장. CSS 커스텀 프로퍼티(`--bg`, `--fg`, `--accent` 등)로 테마 전환을 단일 지점에서 관리 — 무빌드 환경에서 별도 CSS-in-JS 없이 가장 값싸게 구현 가능한 방식.

### 3.3 색각 이상 대응 — 자원 색상 구분

WCAG 1.4.1(Use of Color) 확인 결과: **"색상은 정보 전달·구분의 유일한 수단이 되어서는 안 된다"**가 명문 요구사항이다.

이 프로젝트에 직접 해당하는 지점: 레시피/레퍼런스 표에서 자원(철광석/구리/석탄 등)이나 상태(부족/충분/과잉)를 색상으로 구분하는 UI가 나올 가능성이 높다(계산기, 공장 단계도).

**적용 방법(구체적)**:
- 자원 아이콘을 항상 색상과 함께 표시 — 아이콘 자체가 이미 이 앱의 27개 건물 아이콘처럼 존재하므로, 색상에 아이콘/텍스트 라벨을 병행하면 별도 비용이 거의 없다.
- 배관/배선 다이어그램에서 "유체 종류"를 색으로만 구분하지 말고 선 패턴(실선/점선)이나 라벨을 병행한다.
- 상태 표시(부족/충분)는 색상 + 기호(▲▼ 또는 ✓✗)를 함께 쓴다.
- 색 대비는 색맹 시뮬레이션 기준으로도 3:1 이상 명도 차를 확보한다(적록색약이 가장 흔하므로 빨강/초록 인접 색상 쌍을 피하고 파랑/주황 계열로 대체하는 게 실무적으로 안전).

### 3.4 축소된 모션 (`prefers-reduced-motion`)

- 이 앱에서 모션이 발생하는 지점은 명확히 두 곳: **맵 줌/팬 애니메이션**(부드러운 확대 트랜지션), **체크리스트 완료 시 마이크로 인터랙션**.
- `@media (prefers-reduced-motion: reduce)` 안에서 트랜지션 지속시간을 0에 가깝게 줄이거나 즉시 상태 전환으로 대체한다. 특히 확대/축소·패닝은 전정 장애 유발 가능성이 높은 모션 유형으로 명시되어 있으므로(스케일링·패닝·회전이 고위험군), 맵 화면은 우선 대응 대상 1순위다.
- 구현 비용은 CSS 미디어쿼리 블록 하나로 끝나므로 처음부터 넣는 게 나중에 추가하는 것보다 싸다.

## 4. i18n — 한국어 1차 + 영어 선택

### 4.1 무빌드 환경에서의 실용적 다국어 구조

빌드 스텝(i18next, react-intl 등 프레임워크 의존)이 없는 전제이므로, 구조는 최대한 단순해야 한다.

**권고 구조**:
```
/data/i18n/ko.json
/data/i18n/en.json
```
각 파일은 flat 키-값(중첩 최소화, 예: `"milestone.tier1.title"`) JSON. 런타임에 `fetch`로 로드 후 두 가지 치환 방식을 병행:
- 정적 텍스트: HTML에 `data-i18n="milestone.tier1.title"` 속성을 달고, 로드 시 `document.querySelectorAll('[data-i18n]')`를 순회하며 `textContent` 치환.
- 동적/템플릿 텍스트(계산기 결과 등): JS 코드에서 `t('key', {count: n})` 형태의 작은 헬퍼 함수로 직접 사용.

이 패턴은 프레임워크 없이도 안정적으로 쓰이는 방식이며(바닐라 JS i18n의 표준적인 최소 구현), 데이터(레시피/마일스톤 JSON)와 UI 텍스트(i18n JSON)를 분리해두면 언어 전환 시 데이터 재요청 없이 라벨만 바뀐다.

### 4.2 데이터 JSON 자체의 다국어 처리

레시피/건물 JSON이 Docs.json에서 생성된다면, 이름 필드를 `{"ko": "...", "en": "..."}` 객체로 갖는 편이 이후 확장(용어집 등)에 유리하다 — 별도 i18n 딕셔너리와 중복 관리하지 않고 데이터 자체에 다국어를 내장.

### 4.3 게임 용어 한/영 병기 관행

Satisfactory 같은 게임의 한국 커뮤니티(공식 로컬라이징 + 팬 위키)에서 일반적으로 관찰되는 패턴:
- **최초 등장 시 국문 뒤 괄호로 영문 원어 병기**: 예) "철광석(Iron Ore)", "조립기(Assembler)", "과부하 방지기(Power Shard)".
- 이후 본문에서는 국문만 사용하되, 표/레퍼런스처럼 정확한 대조가 필요한 곳(레시피 표, 용어집)에서는 열을 따로 두어 영문을 병기.
- 용어집(⑤ 화면) 자체가 "국문 용어 ↔ 영문 원어 ↔ 설명"의 3열 구조를 취하는 게 이 앱의 "학습 레이어" 목적에 부합 — 플레이어가 영문 위키/디스코드 자료를 찾아볼 때 용어를 매칭할 수 있어야 하기 때문.

**권고**: i18n 토글은 "UI 언어 전환"이 아니라 "용어 표기 방식"으로 프레이밍하는 게 이 앱에 더 맞을 수 있다 — 완전한 영문 UI 번역보다, 국문 UI + 게임 용어 옆 영문 병기 토글이 실사용 가치가 크다(개발 부담도 훨씬 낮다: UI 문자열 전체가 아니라 용어 사전만 관리하면 됨). 다만 브리핑에서 "영어는 선택적"이라 했으므로 최소 대응은 4.1의 완전 이중 언어 구조를 준비해두고, 실제 영문 번역은 용어 위주로 먼저 채우는 점진적 접근을 권한다.
