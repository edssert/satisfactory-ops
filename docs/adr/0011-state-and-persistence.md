# ADR-0011: 상태는 signals 스토어, 영속은 버전드 localStorage

- **상태**: 채택
- **날짜**: 2026-08-19
- **관련 리서치**: `docs/research/arch-scope-quality.md`, `data-clientside.md`
- **관련 결정**: ADR-0009, ADR-0010, ADR-0012

## 맥락
이 앱의 화면들은 독립적이지 않다. 마일스톤 체크 하나가 계산기의 사용 가능 레시피, 기본 벨트 티어,
맵의 강조 노드, 용어집의 잠금 해제를 동시에 바꾼다(FRD F1-4, F1-5). 이 파생 관계를 어디에 둘지,
그리고 사용자의 100시간짜리 진척을 어떻게 잃지 않을지 정해야 한다.

Astro 정적 페이지 + 아일랜드 구조에서는 상태가 **페이지 전환을 넘어 살아남아야** 한다.

## 결정

**`@preact/signals` 스토어 + `localStorage` 영속. 스키마는 버전드이며 마이그레이션 사다리를 갖는다.**

```
src/state/
  progress.ts   마일스톤 체크·현재 티어·해금 대체 레시피
  setup.ts      게임 설정(시작 지점, 튜토리얼 스킵, 자원 랜덤화)
  persist.ts    load/save/migrate/export/import  ← 유일하게 localStorage를 만지는 곳
```

1. 스토어는 **순수 TS 모듈**이다. 아일랜드는 이것을 import할 뿐, 상태를 소유하지 않는다.
   페이지가 바뀌면 아일랜드는 재마운트되지만 상태는 localStorage에서 복원된다.
2. 저장 키는 `sfops.v1` 하나. 최상위에 `schemaVersion`을 둔다 (TRD D-1).
3. 마이그레이션은 **버전별 함수 체인**이다. `migrate(1→2)`, `migrate(2→3)` … 순차 적용.
   마이그레이션 없는 파괴적 스키마 변경을 금지한다 (TRD D-2).
4. 마이그레이션 실패 시 **원본을 `sfops.v1.backup.<timestamp>`로 보존**하고 사용자에게 알린다 (TRD D-3).
5. 쓰기는 400ms 디바운스. 파생값은 `computed`로 만들고 저장하지 않는다 — **저장하는 것은 사용자가 입력한 사실뿐**이다.
6. 내보내기/가져오기 JSON을 제공한다 (TRD D-4). 세이브 임포트 등 대량 변경 전 자동 백업 (TRD D-5).

## 근거
1. 파생값(현재 티어, 다음 할 일 3가지, 사용 가능 레시피)을 저장하면 게임 데이터가 갱신될 때 **낡은 파생값이
   남는다.** 입력 사실만 저장하고 나머지를 계산하면 이 문제가 존재하지 않는다.
2. `localStorage`는 동기 API라 아일랜드 마운트 시 깜빡임 없이 초기 상태를 읽을 수 있다. IndexedDB는 비동기라
   같은 자리에서 로딩 상태를 처리해야 한다. 진척 데이터는 수 KB라 용량 이점도 없다.
3. 게임 데이터와 사용자 데이터를 물리적으로 분리한다(TRD 4.1) — 게임 데이터는 빌드 산출물, 사용자 데이터는
   localStorage. 게임 갱신이 사용자 데이터를 훼손할 경로가 없다.

## 결과
- **브라우저 데이터 삭제 시 진척이 사라진다.** 시크릿 모드, iOS의 장기 미사용 스토리지 정리도 위험이다.
  → 완화: 내보내기 UX를 눈에 띄는 자리에 두고, iOS 사용자에게 홈 화면 추가를 안내한다. 완전한 방어는 아니다.
- `user.github.io` origin을 다른 프로젝트와 공유한다 → 키 네임스페이싱(`sfops.`)으로 충돌만 피한다.
- 아일랜드가 페이지마다 재마운트되므로, 스토어 초기화는 **멱등**이어야 한다.

## 검토한 대안
- **IndexedDB**: 비동기라 초기 렌더가 복잡해지고, 수 KB 데이터에 이점이 없다. 세이브 파서(F10)가 대용량
  중간 산출물을 다루게 되면 그때 별도 저장소로 도입한다 — 진척 상태와는 분리한다
- **URL에만 상태 저장**: 공유는 되지만 영속이 안 된다. 공유용으로 병행하되 정본으로 쓰지 않는다
- **상태관리 라이브러리(zustand/nanostores)**: 스토어 3개에 의존성을 늘릴 이유가 없다. signals로 충분하다
