# ADR-0012: 게임 데이터는 빌드타임에 화면별 페이로드로 쪼갠다

- **상태**: 채택
- **날짜**: 2026-08-19
- **관련 리서치**: `docs/research/data-browser-db.md`, `data-modeling.md`, `data-clientside.md`, `data-server-sql.md`
- **관련 결정**: ADR-0008(원본 소스), ADR-0009(아키텍처), ADR-0011(사용자 데이터)

## 맥락

`scripts/build-data.mjs`가 게임 원본에서 생성한 정규화 JSON은 현재 **2.2MB / 8개 파일**이다
(items 524KB, recipes 735KB, buildings 456KB, schematics 392KB …). 이것은 **파이프라인의 산출물**이지
**앱이 브라우저로 내려보낼 페이로드**가 아니다. 예를 들어 items.json의 750개 항목에는 앱이 절대 쓰지 않는
`radioactiveDecay`, `canBeDiscarded`, 아이콘 경로 문자열 등이 들어 있다.

동시에 한국어 표시명 문제가 있었다. 게임은 로케일별 데이터 파일 56개를 배포하며 `ko.json`에 **공식 한국어
표시명**이 있다(ADR-0017). 이것을 쓰지 않으면 화면의 한글 이름을 사람이 타이핑하게 되고, 그것이 정확히
`bd981f4`·`2b5cdad`에서 사고를 낸 경로다.

## 결정

**2단 파이프라인을 둔다. 원본 정규화(1단)와 앱 페이로드 생성(2단)을 분리한다.**

```
게임 Docs/en-US.json ─┐
                      ├→ [1단] scripts/build-data.mjs  → src/data/*.json      (원본 정규화, 전량)
게임 Docs/ko.json   ──┘                                 src/data/ko/*.json    (한국어 표시명)
                                                              │
src/data/curated/*.json (수기: 마일스톤 조언·부지·용어) ──────┤
                                                              ↓
                                        [2단] scripts/build-app-data.mjs
                                                              ↓
                                        src/data/app/*.json  (화면별 최소 페이로드 + 역인덱스)
```

1. **1단은 건드리지 않는다.** ADR-0008의 계약(sha256·buildid 기록, 13개 새니티 게이트)이 그대로 유지된다.
2. **2단이 앱이 실제로 쓰는 것만 뽑는다.** en/ko를 클래스명으로 조인해 `{ id, ko, en, ... }` 형태로 만들고,
   화면이 필요로 하는 필드만 남긴다.
3. **역인덱스를 빌드타임에 만든다.** `아이템 → 이 아이템을 만드는 레시피[]`, `아이템 → 이 아이템을 쓰는 레시피[]`,
   `건물 → 레시피[]`, `티어 → 마일스톤[]`. 런타임에 872개를 순회하지 않는다.
4. **수기 콘텐츠는 클래스명으로만 참조한다.** `"강화 철판"`이 아니라 `"Desc_IronPlateReinforced_C"`.
   존재하지 않는 클래스를 참조하면 **빌드가 실패한다**.
5. **런타임 데이터베이스를 두지 않는다.** IndexedDB·SQLite WASM 모두 채택하지 않는다.
6. **드리프트 감지**: 2단은 현재 게임 파일의 sha256을 `meta.json`과 비교해, 다르면 경고하고
   `--strict`에서는 실패한다. 사이트 푸터에 기준 게임 버전(`steamBuildId`)을 상시 표기한다.

## 근거
1. **정적 페이지에는 데이터 페이로드가 대부분 필요 없다.** Astro가 빌드타임에 HTML로 굳히므로, 용어집·레퍼런스
   표·랜딩은 JSON을 0바이트도 내려받지 않는다. 브라우저로 데이터를 보내는 화면은 계산기 정도다.
2. **SQLite WASM은 TRD P-3(초기 JS 150KB)를 즉시 위반한다.** WASM만 1MB+다. 재귀 CTE의 표현력은 매력적이지만,
   이 데이터 규모(872행)에서 JS 객체 순회보다 빠를 이유가 없다.
3. **IndexedDB는 이 데이터에 이점이 없다.** 게임 데이터는 읽기 전용이고 배포마다 통째로 바뀐다. 저장했다가
   버전이 바뀌면 무효화 로직이 필요해지는데, 그 복잡도를 살 이유가 없다. HTTP 캐시 + 서비스워커가 같은 일을 한다.
4. **역인덱스를 런타임에 만들면 매 진입마다 만든다.** 빌드에서 한 번 만들면 영원히 공짜다.

## 결과
- 데이터 갱신 절차가 2단계가 된다: `build-data.mjs` → `build-app-data.mjs`. 후자를 잊으면 화면이 낡는다.
  → 완화: `npm run data`가 둘을 순서대로 돌린다. CI는 앱 데이터가 최신인지 검사한다.
- `src/data/ko/`가 추가되어 저장소 크기가 늘어난다 (약 2.1MB). 앱 페이로드가 아니라 소스이므로 배포에는 포함되지 않는다.
- 계산기가 순환 레시피까지 다루려면 전체 레시피 인덱스가 필요하다 → 그 화면에서만 지연 로드한다 (ADR-0013).

## 검토한 대안
| 대안 | 기각 사유 |
|---|---|
| **원본 JSON을 그대로 fetch** | 2.2MB. TRD P-2(전체 로딩 3초) 위반. 앱이 안 쓰는 필드가 대부분 |
| **IndexedDB에 전량 적재** | 읽기 전용 데이터에 무효화 로직만 추가된다. 이점 없음 |
| **SQLite WASM (sql.js)** | WASM 1MB+로 P-3 위반. 872행에 SQL 엔진은 과잉 |
| **런타임에 역인덱스 생성** | 화면 진입마다 872개 순회. 빌드타임에 한 번이면 되는 일 |
| **한국어 이름을 수기 사전으로 관리** | 750개 아이템을 손으로 번역·유지. 게임 패치마다 재검수. 공식 로케일이 있는데 할 이유가 없다 |
