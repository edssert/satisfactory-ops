# 제품 디자인 시스템

## 1. 목적

Satisfactory Ops의 화면을 실제 게임 데이터, 공장 설계 작업, 검증 결과가 하나의 시각 언어로 이어지는
제품 경험으로 정의한다. 이 문서는 특정 구현을 영구 고정하는 규제 목록이 아니다. 새 기술과 표현은
제품 적합성, 실제 콘텐츠, 접근성, 성능 및 회귀 검증을 충족하면 파일럿을 거쳐 정본으로 승격한다.

CSS 토큰의 실행 정본은 `src/styles/tokens.css`다. 이 문서는 토큰의 의미, 화면별 밀도, 모션 역할,
자산 사용 및 진화 절차를 기록한다.

## 2. 디자인 판독

| 항목 | 정의 |
|---|---|
| 제품 | Satisfactory 생산 계산·실축 배치·물류 연결·검증·도면 발행 도구 |
| 사용자 | 한국어 플레이어, 공장 최적화·확장·시공을 반복하는 장기 사용자 |
| 핵심 과업 | 목표량 계산 → 설비 구성 → 실제 크기 배치 → 벨트·파이프 연결 → 검증 → 도면 발행 |
| 정보 밀도 | 랜딩 중밀도, 문서 중밀도, 계산·설계 화면 고밀도 |
| 신뢰 조건 | 게임 데이터 출처, 실축 점유 영역, 포트 방향, 처리량, 검증 상태가 화면에서 추적 가능해야 함 |
| 시각 논지 | **FICSIT 현장 운영체제 × 살아 있는 실축 공장 모델** |

이 제품은 일반 SaaS 대시보드처럼 보이는 것이 목표가 아니다. 사용자가 랜딩에서 본 공장 조각이 계산기,
설계 스튜디오, 도면 내보내기에서도 같은 자산·좌표·처리량 모델로 이어지는 것이 목표다.

## 3. 표현 제어값

| 화면 | 표현성 | 밀도 | 모션 | 물성 | 설계 의도 |
|---|---:|---:|---:|---:|---|
| 랜딩 | 8/10 | 5/10 | 8/10 | 7/10 | 실제 공장이 조립·배선·검증되는 과정을 스크롤 서사로 체험 |
| 계산기 | 4/10 | 8/10 | 4/10 | 4/10 | 입력·결과·제약의 비교와 수정 속도를 우선 |
| 설계 스튜디오 | 6/10 | 9/10 | 5/10 | 6/10 | 실제 탑뷰와 운송 레이어를 장시간 정밀 조작 |
| 가이드·도감 | 5/10 | 6/10 | 3/10 | 5/10 | 진행 판단과 게임 데이터 탐색을 빠르게 스캔 |

제어값은 표현 강도를 조정하는 기준이며 새 표현을 차단하는 상한이 아니다. 파일럿에서 과업 성공률과
브라우저 검증 결과가 개선되면 값을 갱신한다.

## 4. 근거와 기술 채택

조사일은 2026-08-21이다. 저장소 별 수와 활동은 변동 가능하며 `[[frontend-landing-technology-2026]]`에서
접근일과 근거를 관리한다.

| 기술·근거 | 현재 역할 | 제품 적용 |
|---|---|---|
| Astro 7 | 정적 HTML, 아일랜드, 브라우저 View Transitions | 콘텐츠와 값은 HTML로 제공하고 페이지 전환의 시각 연속성을 강화 |
| GSAP 3.15 + ScrollTrigger + SplitText | 랜딩의 핀·스크럽·타임라인·텍스트 장면 | 목표 → 계산 → 배치 → 라우팅 → 검증의 다단계 스크롤 장면 |
| Lenis 1.3.26 | 네이티브 스크롤 기반 입력 보간과 GSAP/WebGL 동기화 | 랜딩에 적용하고 앵커, 중첩 스크롤, 축소 모션을 공식 옵션으로 보존 |
| Motion 13 | Preact/DOM의 제스처·스프링·레이아웃 전환 | 계산 결과 재정렬, 선택 패널, 편집기 마이크로 인터랙션 |
| CSS Scroll-driven Animations | 저비용 점진 향상 | 지원 브라우저에서 장식 레이어와 진행 상태를 CSS로 실행, 정적 폴백 유지 |
| Three.js | 실제 게임 메시 기반 3D 장면 | 실제 추출 메시가 준비된 랜딩 공장 조각과 자산 검수 파일럿에 사용 |
| Google DESIGN.md | 토큰과 의도를 함께 검증하는 문서 방식 | 현재 CSS 토큰을 유지하면서 문서 링크·대비·변경 검증을 자동화 |

GSAP과 Motion은 중복 경쟁 라이브러리로 사용하지 않는다. GSAP은 스크롤 서사와 복합 타임라인,
Motion은 상태 소유 Preact 아일랜드의 제스처와 레이아웃 전환을 담당한다. 이 구분은 새 기능의 성격에 따라
벤치마크 후 변경할 수 있다.

## 5. 랜딩 경험 구조

### 5.1 장면 1 — 실체가 있는 히어로

첫 화면은 일반 공장 사진 대신 설계 스튜디오와 같은 탑뷰·파운데이션·컨베이어 자산으로 구성한 실제 공장
조각을 사용한다. 사용자의 포인터 또는 스크롤에 따라 설비 점유 프레임, 포트, 처리량이 순차적으로 드러난다.
텍스트는 제품 약속과 즉시 실행 가능한 `계산 시작`, `설계 스튜디오 열기` 행동을 제공한다.

### 5.2 장면 2 — 하나의 모델이 완성되는 과정

하나의 핀 섹션에서 동일 데이터가 다음 상태로 전환된다.

1. 목표 품목과 분당 생산량
2. 레시피·대체 레시피를 반영한 생산 그래프
3. 실제 크기의 설비와 파운데이션
4. 포트에 접속된 컨베이어·파이프·리프트
5. 처리량·충돌·지지·방향 검증 오버레이
6. 독립 SVG/PNG 도면 발행 상태

장면 사이에서 다른 이미지를 교체하지 않고 동일 객체의 상태와 레이어를 변화시켜 제품의 데이터 연속성을
증명한다.

### 5.3 장면 3 — 조작 가능한 제품 증거

랜딩 안에 축소된 설계 스튜디오 데모를 제공한다. 사용자는 설비 선택, 회전, 실제 토대 배치, 한 구간의
컨베이어 연결을 수행할 수 있다. 데모는 별도 장식 구현이 아니라 실제 편집기 도메인과 렌더러의 읽기 전용
또는 제한된 프리셋을 사용한다.

### 5.4 장면 4 — 기능으로 이어지는 전환

각 장면의 CTA는 가이드, 계산기, 설계 스튜디오, 도감의 실제 과업으로 연결한다. Astro 브라우저 View
Transitions를 사용해 선택한 품목·설비·공장 조각이 다음 화면에서도 공간적으로 이어지게 한다.

## 6. 토큰과 테마

### 6.1 토큰 계층

1. `--raw-*`: 색상 원시값. `src/styles/tokens.css`에서 정의한다.
2. 의미 토큰: `--canvas`, `--layer-*`, `--text-*`, `--action-*`, `--status-*`, `--diagram-*`.
3. 컴포넌트 토큰: 편집기 포트, 운송 레이어, 검사 결과처럼 도메인 역할을 표현한다.
4. 이행 별칭: 기존 컴포넌트 마이그레이션 기간에만 유지하며 제거 조건을 기록한다.

새 시각 역할은 의미 토큰과 실제 인접 색 대비를 함께 정의한다. 검증 계약은
**색상 리터럴은 `src/styles/tokens.css` 밖에서 0건**이며, `npm run check:tokens`는 참조 토큰이 모두 선언됐는지와 양 테마의 핵심 역할이 존재하는지
검사한다.

### 6.2 테마

| 테마 | 작업 환경 | 품질 목표 |
|---|---|---|
| 라이트 = 정밀 작업지 | 문서·수치·도면을 밝은 환경에서 장시간 검토 | 토대·격자·치수선과 본문의 안정적 대비 |
| 다크 = 현장 제어실 | 게임과 전환하며 공장 상태·운송 레이어 확인 | 탑뷰와 상태 조명의 구분, 저휘도 장시간 사용 |

새 테마와 고대비 모드는 동일 의미 토큰 계약에 추가할 수 있다. 공개 화면 전체를 한 번에 이행하지 못하는
경우 실험 플래그와 명시된 커버리지로 배포하고, 미이행 영역을 추적한다.

## 7. 타이포그래피와 레이아웃

| 역할 | 서체 | 적용 |
|---|---|---|
| 표시 | Wanted Sans | 랜딩 헤드라인과 큰 장면 전환 |
| 본문·UI | Pretendard | 한국어 본문, 컨트롤, 테이블 |
| 수치·좌표 | JetBrains Mono | 처리량, 치수, 좌표, 검증 상태 |

- 한국어와 영문 클래스명, 긴 레시피명, 단위가 섞인 실제 데이터를 기준으로 줄바꿈을 검증한다.
- 수치 열은 tabular figures와 단위 정렬을 사용한다.
- 문서 폭, 데이터 폭, 캔버스 폭을 분리한다. 전문 도구에 랜딩의 여백 규칙을 복제하지 않는다.
- 화면 폭 375, 768, 1024, 1440px와 200% 확대를 기본 검증 지점으로 사용한다.

## 8. 자산과 도면

자산 승인 기준은 `[[ASSETS]]`가 관리한다. 랜딩과 앱은 다음 품질을 공유한다.

1. 게임과 일치하는 실제 자산 또는 출처가 검증된 탑뷰를 사용한다.
2. 이미지와 점유 프레임을 분리하며 이미지 여백이 실제 크기를 바꾸지 않는다.
3. 기계, 파운데이션, 벨트, 파이프, 리프트는 동일 축척과 깊이 모델에서 합성한다.
4. 생성형 이미지는 게임과 무관한 장식 배경이 아니라 실제 메시·스크린샷의 보정, 재질 후보, 연출
   프로토타입처럼 진위 검증이 가능한 단계에서 사용한다.
5. 랜딩 시각물은 앱의 실제 렌더러와 데이터를 재사용해 제품 화면과 약속이 분리되지 않게 한다.

## 9. 모션 시스템

| 역할 | 구현 | 검증 |
|---|---|---|
| 장면 서사 | GSAP timeline + ScrollTrigger | 스크롤 역방향, 새로고침 중간 진입, 핀 해제 |
| 텍스트·레이어 등장 | SplitText + transform/opacity | HTML 원문 유지, 폰트 로드 후 refresh |
| 입력 보간 | Lenis + GSAP ticker 동기화 | 앵커, 키보드, 중첩 스크롤, 축소 모션 |
| 상태 전환 | Motion 또는 CSS View Transitions | 포커스·선택 상태 유지, 취소 가능성 |
| 저비용 장식 | CSS scroll/view timeline | `@supports` 폴백과 비지원 브라우저 최종 상태 |
| 실제 3D | Three.js render loop | 화면 밖 정지, 저전력 모드, 정적 포스터 폴백 |

애니메이션은 transform과 opacity를 우선하고 DOM 읽기와 쓰기를 배치한다. 핀·스크럽 장면은
`prefers-reduced-motion: reduce`에서 같은 정보를 정적인 순서로 즉시 제공한다. 숫자와 상태의 의미는
항상 HTML 또는 앱 상태에 존재하며 애니메이션이 생성하지 않는다.

## 10. 컴포넌트 상태와 상호작용

모든 상호작용 컴포넌트는 적용 가능한 기본, hover, focus-visible, active, selected, disabled, loading,
empty, error, success 상태를 정의한다. 네이티브 의미 요소를 기본으로 사용하고 복합 위젯은 키보드 과업
테스트를 추가한다.

설계 스튜디오의 시각 계층은 `파운데이션 → 운송 하부 → 설비 → 운송 상부/리프트 → 포트/선택 → 검증
오버레이 → 배치 대기 프리뷰` 순으로 관리한다. 라벨과 UI는 설비 회전에 따라 회전하지 않는다.

## 11. 접근성 및 성능 승인 기준

- WCAG 2.2 AA 대비와 키보드 경로를 자동 검사한다.
- 색상은 텍스트, 형태, 패턴 또는 위치 중 하나 이상의 비색상 단서와 함께 사용한다.
- LCP 장면은 실제 콘텐츠를 가리지 않고 정적 포스터 상태에서 먼저 완성된다.
- 큰 3D·영상·모션 청크는 해당 장면 접근 시 로드하고 화면 밖에서 실행을 중단한다.
- 저성능·축소 모션·JS 비활성 환경도 동일 CTA와 핵심 제품 설명에 접근할 수 있다.

## 12. 진화 절차

1. 새 기술·표현 후보를 `research`에 출처, 접근일, 유지보수 상태, 제품 적용 가설과 함께 기록한다.
2. 실제 데이터와 실제 자산을 사용하는 한 장면 또는 한 컴포넌트로 파일럿을 만든다.
3. 375·768·1024·1440px, 200% 확대, 키보드, 축소 모션, 콘솔·네트워크, 프레임 안정성을 검증한다.
4. 기존 대비 과업 전달력·조작성·성능이 개선되면 이 문서와 토큰·컴포넌트를 함께 갱신한다.
5. 개선되지 않은 후보는 영구 금지 대신 재검토 조건과 측정 결과를 남긴다.

이 절차는 새 도입을 억제하기 위한 승인이 아니라, 고품질 기술이 일회성 데모로 끝나지 않고 제품 전체로
확장되게 하는 승격 절차다.

## 13. 검증 명령

```bash
npm run check:docs
npm run check:tokens
npm run build
npm run test:nojs
npm run test:scroll
npm run test:theme
node scripts/verify-accessibility.mjs
```

렌더 변경은 실제 브라우저에서 375·768·1024·1440px과 200% 확대를 캡처하고, 랜딩의 핵심 장면은
축소 모션과 일반 모션을 모두 검토한다.
